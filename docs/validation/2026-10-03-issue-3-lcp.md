# Issue #3: responsive hero delivery

Observed on 2026-10-03. Follow-up to [the initial rendering validation](2026-10-03-rendering-analytics.md).

The existing commit de34b10 already removes the loader and CSS/GSAP hiding of hero text, navigation, and CTAs. This change keeps that behavior and reduces image delivery costs on the home, service, and article templates. The before/after comparison below uses three comparable mobile PSI runs per URL on the public production domain.

## Changes and local evidence

The browser PSI baseline identifies a render-blocking stylesheet and estimates 2,630ms savings on the home. Astro now inlines route CSS, and Barba retains/deduplicates inline styles on navigation. Sharp 0.34.5 is an explicit build dependency: the first Vercel preview failed to find the previously optional dependency.

`src/data/heroImages.ts` generates WebP candidates at build time from the existing public images. Each template supplies sizes matching its layout. The home preload uses the same responsive candidates as the portrait and applies only above 960px, where the portrait sits beside the text. Barba removes/replaces page-specific image preloads while preserving shared font preloads. The post-build patch rewrites every responsive candidate relative to its output HTML, including later entries in srcset/imagesrcset.

Image dimensions now come from the source metadata. The home portrait is 1086 × 1448 and the timeline article image is 1672 × 941; their previous HTML dimensions did not match the files. Existing CSS frames, object-fit, and visual composition are preserved.

Chrome at 390 × 844 selected the 400px variants in this environment; higher-density devices may select larger files. Full candidate sizes and paths are in [the image evidence](issue-3-image-delivery.json).

Local production-build checks:

- `pnpm run build` passes, including the post-build patch; 28 pages generated.
- `pnpm run test --maxWorkers=1` passes: 6 files, 12 tests in the isolated worktree. Earlier root-checkout counts also included a temporary duplicate checkout and are not the authoritative suite count. The sandbox initially prevented esbuild from reading parent directories; the suite passed outside the sandbox.
- All 55 responsive candidates across 28 generated HTML files resolve to existing files. Regression coverage checks root/nested HTML and both quote styles.
- Chrome at 390 × 844: home, Belém, and article H1/text remain visible; no horizontal overflow; hero images load. Home and Belém WhatsApp CTAs are visible and retain their destinations.
- Mobile menu opens; home → Belém and article → home Barba navigation work. Title/canonical update, and the home image preload is restored on return.
- Desktop home at 1440 × 900 retains its text/portrait layout. Temporary viewport overrides were reset.

Font faces already use font-display swap and critical text font preloads. No CSS hiding remains on the hero. The new PSI diagnostic supports testing CSS inlining. Font faces and preload weights are unchanged; image-size reductions alone do not establish a causal LCP improvement.

## Protected preview limitation

The repaired [preview deployment](https://luanalves-ipcfyl19p-aka-luans-projects.vercel.app/) is Ready on Vercel and works in the authenticated browser. Unauthenticated requests return HTTP 302 to vercel.com/sso-api. PSI follows that redirect and measures Vercel authentication rather than this site. The attempted preview reports are rejected and cannot be used as after metrics. See [the access evidence](issue-3-preview-access.json). This is consistent with [Vercel Authentication behavior](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication).

The owner approved publication. Final measurements use the public production domain after PRs #19, #20, and #21; no protection settings or bypass credentials were changed. The rejected authentication-page measurements remain excluded. Field data is unavailable; TBT is not INP.

## Production follow-up

PR #19 was approved, merged as b45275d, and published on 2026-10-03 (Vercel deployment dpl_37dX6A4ALVw7pebJp5zobHD7pwLU). The public HTML has one inline style and zero external stylesheet links, with responsive hero candidates.

Initial after measurements showed a home CLS increase (0, 0.006, 0.041 in independent samples). The report identifies the mobile nav and hero actions as culprits. A local comparison with all font requests returning 404 reproduces a four-line fallback headline versus three lines with Newsreader. Its ch-based width changes with the font. A 6em limit accommodates the authored line breaks in both fonts, and an explicit mobile eyebrow line-height fixes its font-dependent height. At 390x844, loaded and unavailable fonts now produce identical title height (157.3125px), lead top (397.28125px), and actions top (544.46875px), without overflow. The nav's initial mobile CSS now matches the controller's margin/padding/background so boot does not move it. The final production comparison below measures the complete stability correction.

PR #20 (db89781) fixed the mobile header position and fallback headline height. Its [nine-run measurement](issue-3-psi-intermediate-2.json) still identified one home shift on the heading span (0.011): the shrink-to-fit box changes width with the font. The final correction gives the heading an explicit available width, bounded by 6em, and makes its child span a block. Loaded and unavailable fonts now share both box dimensions (331.1875 x 157.3125px at 390px) and the same CTA top (544.46875px). Text, font, authored breaks, and desktop composition are preserved.

### Remaining observed costs

The final home [report](https://pagespeed.web.dev/analysis/https-luanalves-com-br/okctxujrhv?form_factor=mobile) identifies the visible heading span as LCP and reports 190ms element render delay. Its dependency tree still includes multiple Manrope and Newsreader faces and the 309.15KiB Material Symbols font; the latter is much larger than the responsive mobile hero variants. The [Belém report](https://pagespeed.web.dev/analysis/https-luanalves-com-br-criacao-de-sites-belem/askgrl0rbp?form_factor=mobile) identifies the H1 with 270ms element render delay. The [article report](https://pagespeed.web.dev/analysis/https-luanalves-com-br-insights-quanto-tempo-leva-para-criar-um-site-profissional/skjutl6vi6?form_factor=mobile) identifies the responsive hero image, with 50ms resource delay, 30ms load duration, and 120ms render delay. These diagnostic trace timings are distinct from simulated lab LCP; do not sum them to reconstruct the score.

The final reports still flag roughly 88–89KiB unused JavaScript and some long tasks. Fonts, the large icon font, and boot/analytics JavaScript remain profiling candidates under constrained network/CPU. Those requests and rendering delays are observed; attributing the remaining median to any one resource would require an isolated experiment. Font/icon subsetting and reducing initial JS are the next focused investigations. Hero visibility no longer waits for a loader or animation, and there is no external blocking stylesheet in the verified production HTML.
